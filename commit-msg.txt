[SEC-13] Fix: NoSQL regex injection in user email lookup

Found this one through source code review rather than live testing
first. The getUserByEmail function, used during both login and
registration duplicate checks, built a regex search pattern
directly out of whatever email string was passed in, with no
escaping of special regex characters at all.

The main risk is that dots are extremely common in real email
addresses, but a dot has a special meaning in regex, it means match
any single character, not literally a dot. This meant the email
lookup was never doing a truly exact match like it should for
something like a login check.

Initially suspected this could also cause a crash via malformed
regex syntax, tested that first and found it was actually already
blocked by the existing Zod email format validation, so that
specific angle was not exploitable. Refined testing toward the
wildcard matching issue instead, which validly formatted emails can
still trigger since dots are completely normal in real addresses.

Proved this live by logging in with a deliberately wrong email,
replacing the real dot in my test accounts email with a literal dot
in a different position, and confirming the server still found and
matched the real account, shown by receiving an invalid credentials
response instead of user not found, despite submitting a string
that was not the real stored email.

Fixed by replacing the regex based lookup entirely with a plain
exact match query using Mongoose's collation option for proper
case insensitive matching, which removes the need for building any
regex from user input at all, eliminating the injection vector
completely rather than just sanitizing around it.

Retested after the fix using the exact same wildcard payload and
confirmed it now correctly returns user not found. Also confirmed
normal legitimate login still works correctly afterward.
