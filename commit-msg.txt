[SEC-06] Fix: Insecure file upload validation using client-controlled MIME type

Found that the profile picture and product image upload endpoints
only checked the Content-Type header the client sent along with
the file, to decide whether it was a real image or not. This header
is fully controlled by whoever is sending the request and is not
verified against the actual file content in any way, so its
trivial to lie about it.

Proved this by creating a plain text file containing a script tag,
naming it fake-image.png, and uploading it while manually setting
its Content-Type to image/png. The server accepted it without any
issue and stored it in the public uploads folder, where it was
then reachable by anyone through a direct URL with no login
required at all, since that folder is served as static files.

Fixed by installing the file-type package and adding a second
validation step that runs after the file is uploaded, which reads
the files actual binary content and checks its real file signature
against a list of genuinely allowed image types, completely
ignoring whatever Content-Type the client claimed. If the real
content does not match an allowed image type, the uploaded file is
immediately deleted from disk and the request is rejected.

Also fixed a separate bug in this same file where the uuid package
was being imported incorrectly for the installed version, which
would have caused a crash on every upload attempt.

Retested after the fix using the exact same disguised file and
Content-Type lie as before, and confirmed the server now rejects it
with a clear error message and does not save the file. Also
confirmed a real image file still uploads successfully, so the fix
does not break legitimate functionality.
